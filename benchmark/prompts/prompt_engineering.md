# 提示词工程实战：L1 路由评测 route 64%→98%（项目复盘 / 面试准备）

> 一句话：给**弱模型（qwen3-8b）**写造价 agent 的路由提示词，用**评测驱动**的方式，
> 把「识别用户意图 → 调对工具」的准确率从 64% 迭代到 97.78%，并在过程中修掉一个
> **拒答时编造标准号的安全红线**。本文按「问题 → 诊断 → 解法 → 结果」罗列，结合具体 query。

---

## 〇、先分清：这不是普通的「意图分类」提示词

一句话：**普通「识别意图→调 function」提示词，是给「一次选一个函数的分类器」写的静态说明书；
deer-flow 的 lead_agent 提示词，是给「跑在有状态、动态工具、多智能体 harness 里的编排者」写的运行时模板。**
后者难得多，而且下文这些坑**大半是架构带来的，不是「意图分类」本身的问题**。

| 维度 | 普通 intent→tool 提示词 | deer-flow lead_agent 提示词 |
|---|---|---|
| **角色** | 选一个 function + 填参 | 路由器 + 编排者 + 把关者：委派后**转述**返回，不亲自答专业内容 |
| **提示词形态** | 自包含静态文本 | **运行时模板**，含 harness 注入的占位符（`{soul}` / `{skills_section}` / `{deferred_tools_section}` / `{subagent_section}`） |
| **工具面** | 固定 function list，全暴露 | **动态、分层**：MCP 工具 deferred（藏在 `tool_search` 后按需 promote）、skills、子智能体（`task`）、整单 workflow 状态机 |
| **轮次/状态** | 多为单轮无状态 | 多轮 + checkpointer 持久化 + **HITL**（`ask_clarification` 触发中间件中断等人、workflow 有 resume 契约） |
| **执行层** | 一个 loop 调 function | 18 个中间件（沙箱/摘要/循环检测/去重…）包着，提示词要和它们**协同** |
| **安全红线** | 只能靠文字「祈祷」 | 提示词祈祷 + **确定性代码守卫双层**（`verify_norm`/`verify_cost` 回查、region/spec 口径闸硬拒） |
| **委派层级** | 只有「调 function」一档 | 「直调工具 / 派子智能体(隔离上下文) / 启 workflow」三档，要判走哪档 |

**为什么这决定了坑长什么样**（下文详解）：
- 「先检索」要写成**硬闸**——因为 ce-rag 被 `DeferredToolFilterMiddleware` 藏起，模型必须先 `tool_search`
  promote 才能调（普通 router 工具全暴露、没这一跳）；
- **工具幻觉**——harness 有「skill」这层概念，弱模型分不清 skill 名和工具名，去调不存在的 `norm-qa`；
- **红线泛化打架**——多条规则 + 优先级共存，弱模型选错那条（普通 router 通常就一句「选对 function」，规则少）；
- **委派 vs 直调的判断**——lead 要决定「规范问答自己做 / 组价派 workflow / 复核派 cost-critic」，这是编排者才有的维度。

**结论：lead_agent 的提示词工程，难在「在一个活的系统里和动态工具面 / 多轮状态 / 中间件 / 确定性守卫 /
子智能体委派协同」，而不在意图分类本身。** 本文讲的正是这种协同下、弱模型的稳定性怎么一版版调出来。

## 一、背景（一分钟讲清）

- **系统**：深圳市房建专业智能组价 agent。`lead agent` 只做「意图识别 → 路由到对的工具/子智能体」，
  专业内容（编码/条文/价格/计算）一律经工具产出，绝不凭模型知识作答。
- **模型**：本地 vLLM 部署的 **Qwen3-8B**——弱模型，function-calling / 多步编排不稳，这是所有问题的底色。
- **评测层 L1**：只测「第一次工具决策」——路由对错在 agent 第一个带 `tool_calls` 的消息就定了。三个正交指标：
  - `route_ok`：该调工具就调、该拒就拒（`expect_route` vs 实际是否调了路由工具）；
  - `clarify_ok`：该反问就反问、不该问别问（红线，门 0.95）；
  - `subagent_ok`：该委派子智能体就派对（本集已无委派靶，恒 nan）。
- **起点**：把 `norm-qa` 从**委派子智能体**收敛为 **lead 亲自做的 skill**（动因：子智能体隔离对单跳规范问答
  收益有限，且 MCP 跨 event-loop 崩溃集中在子智能体链上）。改后规范问答由 lead 用前经 `tool_search`
  promote ce-rag 检索工具——**新增一跳**，弱模型可能漏，后续问题多由此长出。

## 二、方法论：评测驱动的提示词工程（面试核心）

**提示词工程在这里不是「写作」，是「带着尺子做实验」。**

```
改一处 → ① F5 手过 3~5 条典型 query（秒级看行为）
       → ② runner 批量出两率（route/clarify）
       → ③ 翻失败用例的 Langfuse trace 归因
       → 再改
```

三条纪律：
1. **一次只改一个变量**。曾经 v3→v4 一把梭（瘦身 + 下沉 + 改 clarify），结果 norm 路由退步了都不知道是哪一刀砍的。
2. **8B 非确定，每版跑 2~3 轮取稳定值**。单轮 ±2~3 条是噪声，别拿单轮下结论。
3. **variant 机制横向比**：每版存 `lead_agent_vN.yaml`，config 切一行，Langfuse `Runs → Compare`，不靠记忆。

**先修「尺子」再优化**——测量不准，优化都是瞎调（见问题 1）。

## 三、问题清单（按发生顺序，结合具体 query）

### 1. 测量污染：`工具=[]` 混了「跑死了」和「真自答」
- **query**：`给"C30现浇混凝土独立基础"组价`（整单）→ 8B 主图打转 → 撞 32k token / 递归上限 → `工具=[]`。
- **根因**：全执行版 runner 跑完整 loop，**路由决策之后**的溢出/打转噪声算进了路由失败。
- **解法**：runner 切**第一次决策版**——第一个带 `tool_calls` 的消息即 break、工具不执行。`工具=[]` 从此
  只剩「真自答」；副产品：不依赖 ce-rag/ce-db 起服务、无 overflow/递归噪声。每条打印 `query=` 便于归因。
- **迁移点**：评测弱 agent 时，把「路由决策」和「决策之后的执行鲁棒性」分开测——后者是另一层（L3/L7）的事。

### 2. 金标口径 vs 模型合理行为（重标 → revert）
- **query**：`帮我算算这面墙` / `这个柱子套什么清单码？` / `帮我给这道墙组价`——零特征业务缺料题。
- **弯路**：一度把 14 条 `expect_clarify→false`（想让 8B route→工具返回 missing→reactive 反问）。
- **根因**：改了金标没同步切提示词哲学；更本质是**金标比 8B 合理行为更严**——「这面墙」零特征直接
  route 给 `bill_match` 没法用，**8B 主动反问才对**，也和原始金标一致。
- **解法**：**revert 重标**。route 64% → **85%**。
- **迁移点**：金标是「尺子」，尺子要贴合合理行为；当数据显示模型行为和金标冲突，先怀疑金标别急着改模型。

### 3. norm 在库题不路由（瘦身丢了「先检索」步骤）
- **query**：`现浇混凝土板的工程量怎么计算？`（GB50854 在库）→ 早期走 tool_search✅、瘦身后 `工具=[]`
  自答；`砖墙的量到底怎么算的` 自答；`这个柱子的工程量是怎么来的` 过度反问。
- **根因**：瘦身版只说「按 norm-qa skill 自做」，没把「先检索」立成**不可跳的第一步**；口语题尤其触发自答。
- **解法**：加 `<norm_qa>` **主图硬闸**——「任何规范/计量/条文题，第一步无条件 `tool_search` 取 ce-rag，
  拿到检索结果前一字不答、也不反问，**无论多口语**」。route 85% → **89%**。
- **迁移点**：给弱模型写提示词，**要把聪明模型会自己想到的步骤全部显式列成不可跳的动作**。瘦身别把关键步骤砍了。

### 4. 工具幻觉：措辞像工具名
- **query**：`独立基础和条形基础包含哪些` / `按2013版装配式预制率怎么核定` → 去调一个**不存在的
  `norm-qa` 工具**（`工具=['norm-qa']`）。
- **根因**：提示词写「按 `norm-qa` skill」，8B 把 "norm-qa" 当成可调工具名。
- **解法**：全程用**真工具名**（`tool_search` / `ce-rag_search_clause` / `verify_norm`），并写死「没有名为
  norm-qa 的工具」。
- **迁移点**：提示词里出现的工具名必须 = 运行时真实注册名（本项目即 `config.yaml tools` = 评测的
  `ROUTE_TOOL_NAMES`）。别造词，弱模型会照着你写的字面去调。

### 5. 过度反问蔓延到清晰题
- **query**：`水泥这阵子涨了吗` / `这个混凝土现在贵不贵`（材料已点名）/ `现浇C30独立基础和预制杯形基础哪个省`
  （构件带规格）——都该直接 route，却被 `ask_clarification` 反问。
- **根因**：clarify 段的例子「帮我算算」太宽，8B **靠例子做模式匹配**，把清晰题也带得反问。
- **解法**：clarify 显式豁免「**材料已点名的询价直接 `price_query`**」「**构件+规格都给的比选直接各自选码**」。
- **迁移点**：弱模型高度依赖你给的例子，**例子选不准会反噬**——正例反例都要给，边界要划清。

### 6. 红线过度泛化 + 拒答编造（最严重，安全红线）⚠️

这是整个过程里最危险、也最能讲清「弱模型 + 提示词」微妙之处的一条。

- **query**：`按GB50011，框架结构的抗震等级怎么划分？`
  （GB50011 是《建筑抗震设计规范》——**结构设计**规范，不属于我们支持的**计量计价**规范，本就不该我们答。）

- **模型实际干了什么（看 trace 里的思考链，一步步）**：
  1. 8B 先正确判断：这是规范条文问题，本该走 `<norm_qa>` 先 `tool_search` 检索；
  2. **但它转念**：提示词里有条红线写「点名 2024版/他省 → 不检索、直接拒」。它把 GB50011 也归进了
     「不支持的规范」这一类，于是推断「**无需检索，直接拒**」——**跳过了检索**；
  3. **最致命的一步**：它没有干净地说「不支持」，而是**凭记忆编了一整套答案**——捏造出
     `DBJ15-9-2019`（广东省抗震规范）、`GB18306-2015`、甲乙丙丁类抗震等级划分……**这些编号和内容工具
     一次都没返回过，全是模型脑补的**。

- **为什么这是最严重的问题**：路由指标（`route_ok`）只看「有没有调工具」，看到 `工具=[]` 只会记一个
  「没路由」。但真正的危害是**模型把编造的假标准号当真答案给了用户**——造价从业者会当真去用。这是
  「专业内容只能来自工具、绝不凭记忆」这条**硬红线被践踏**，而 L1 评测**根本看不见**。

- **根因（两个，叠加）**：
  1. **红线写得太宽，被模型「泛化」了**。我本意是：「点名 2024版/他省地区 → 不检索直接拒」（因为这两种
     我们确定不支持）。但 8B 把它**放大**成了「任何我觉得不支持的规范都不检索直接拒」。GB50011 既不是
     2024 也不是他省，却被套了进去。而且这条红线**优先级最高**，直接压过了 `<norm_qa>` 里「边界题也要
     先检索」的指令——两条规则打架，模型选了错的那条。
  2. **模型「拒答还想帮忙」的本能**：一旦决定拒答，它不甘心只说「不支持」，就顺手凭记忆补一套看起来
     专业的内容——于是编造。

- **解法（对应两个根因）**：
  1. **把边界条件精确枚举，堵死泛化**：写死「**口径超范围**」**只指三种**——① 版本（2024版）② 地区（他省）
     ③ 专业（安装）。并明确「点名某个国标问『怎么规定/怎么计量』（如 GB50011）**不是**口径超范围，是
     **条文问题**，走 `<norm_qa>` 检索」。这样模型不会再把 GB50011 错分到「直接拒」那一桶。
  2. **加一条最高红线「拒答时禁止编造」**：告知不支持某规范时，**只准说**「本系统仅支持 GB50500/GB50854-2013
     深圳房建计量计价，该问题超出收录范围，建议咨询当地造价站」——**绝不附带任何具体条文号、标准号、
     数值、等级划分**，哪怕「记得」也一个字不写。
  - **结果**：实测该 query 从「跳检索 + 编造 DBJ 假号」变成了「`工具=['tool_search']` 老老实实先检索」。

- **迁移点（两条，面试高价值）**：
  1. **给弱模型写红线，边界要精确枚举，不能留模糊空间**。你写「2024/他省不支持」，弱模型会自己脑补成
     「凡是我觉得不支持的都这样」，把规则**放大**去套不该套的场景。规则之间还会打架（这条红线 vs 那条
     检索指令），模型不一定选对——所以宁可啰嗦地把「适用范围」列全，也别用「等」「之类」留白。
  2. **功能指标过了 ≠ 安全**。路由率（调没调对工具）是**功能**指标，它**抓不到「编造」**——模型可以
     「没调工具」但同时「编了一个假答案」，路由指标只会记一个普通失败。**内容真伪（有没有编造）要靠
     专门的「引用忠实性」评测（我们叫 L6）去量**。所以不能只看路由两率漂亮就宣布 OK，安全红线得单独把关。

### 7. 边界题金标不一致
- **query**：`按2024版装配式建筑评价标准，预制率指标怎么核定？` → agent 正确直接拒（`工具=[]`），金标却
  标 `expect_route=true` 判它失败。
- **根因**：该 query 点名「2024版」= 版本口径超范围，该直接拒；却和其它 2024 用例（`按2024国标组价`、
  `GB50856-2024`，均 `expect_route=false`）不一致。**是金标 bug，不是提示词问题。**
- **解法**：改该条 `expect_route true→false` 对齐。route 95.65% → **97.78%**。
- **迁移点**：金标本身要自洽——同类用例口径必须一致，否则会把正确行为判成失败。

### 8. 违规取数（他省护栏）
- **query**：`上海本月螺纹钢信息价多少？` → 8B 调了 `price_query`（上海=他省，本系统只支持深圳，该拒）。
- **状态**：红线有「他省不取数」但 8B 没守住；量级小，护栏待加强（未专门修，记录在案）。

### 9. clarify 的结构性天花板（假缺口 vs 真缺口）
- **query**：`这块现浇板套什么定额？`（`工具=['bill_match']`，route 了没反问）vs
  `给我把这个基础处理下报个数`（`工具=[]`，啥也没干）。
- **洞察**：业务缺料题 **route 和 clarify 两种都合法**（route→工具返回 `missing_features`→reactive 反问
  也对）。前者选了 route = **假缺口**（合法，但金标只认 clarify 就判 miss）；后者啥没干 = **真缺口**。
- **后果**：金标在这类题上强行只认一个正确答案，n=18 且门 0.95 → 须 18/18 才过；只要有一条选了合法的
  route 就到不了。**clarify 卡 ~89% 是「双合法路 vs 单答案金标」的口径摩擦，不全是能力问题。**
- **迁移点**：设计评测时，**一题多解要允许多答案通过**，否则会给完美 agent 也扣分，尺子失真。

## 四、可迁移的提示词工程原则（弱模型版，面试可直接讲）

1. **显式 > 隐式**：把聪明模型会自己补的步骤，全部列成不可跳的编号动作（问题 3）。
2. **红线少而硬、且精确**：只留 3~5 条真红线；边界条件精确枚举，别留模糊词给模型泛化（问题 6）。
3. **工具名 = 运行时注册名**：别造词，弱模型照字面调（问题 4）。
4. **例子选得准**：模型靠例子做模式匹配，正反例都给，边界划清，防反噬（问题 5）。
5. **别让模型凭先验短路**：把判断从「模型脑子」挪到「工具」（先检索再判），先验太强时接受行为+掐死危险后果（问题 6）。
6. **安全红线独立于功能指标**：功能指标（路由率）过了 ≠ 安全（不编造）；编造要专门的忠实性评测抓（问题 6）。
7. **评测方法论**：先修尺子（剔基础设施噪声，问题 1）→ 金标贴合合理行为（问题 2/7/9）→ 一次一个变量、多轮取稳。

## 五、结果与反思

**分数轨迹（route / clarify，第一次决策版口径）**：

| 阶段 | route | 关键动作 |
|---|---|---|
| 错标基线 | 64% | 金标重标错配 |
| revert | 85% | 认了「零特征题主动反问是对的」 |
| v5 | 89% | `<norm_qa>` 硬闸 + 真工具名治幻觉 |
| v6-1 | 95.65% | 拆分口径/条文边界 + 拒答禁编（治编造） |
| v6-2 | 97.78% | 金标修 A27 对齐 |

- **route 97.78% 远超门（0.8）**——提示词从「意图识别→路由」这一环已收敛。
- **clarify ~89% 触到结构天花板**——是「业务缺料题双合法路 vs 金标单答案」的口径摩擦，不是能力问题。
- **最有价值的不是分数，是两个非直觉洞察**：① 弱模型会把过宽的红线泛化去吃别的规则；
  ② 功能指标（路由）抓不到安全问题（编造），安全要独立的忠实性评测把关。

**尚未收的尾巴**：① `按GB50011` 的**编造终审**（第一次决策版在 tool_search 就 break，只证明「走上检索
路」，没验 ce-rag 零召回后的终答是否真不编——需全执行 / L6）；② v6 多轮复稳；③ 他省护栏（上海用例）；
④ 转 L6 `norm_faithful` 量编造。

## 六、附：按意图（能力）分类的问题地图

> 上面第三节按「发生顺序」讲，便于看迭代脉络；本节换一个视角，按 agent 的 **6 类能力（意图）** 归类同一批
> 问题——面试时按能力讲，更容易让人对上「这个系统有哪些能力、每个能力踩过什么坑」。**结论：问题高度集中在
> 规范问答，其余能力零星。**

### 能力① 规范问答（norm QA）—— 绝对重灾区，v4→v6 的主战场

| 子问题 | 触发 query | 现象 | 解法 / 版本 |
|---|---|---|---|
| 1a 在库题不路由 | `现浇混凝土板的工程量怎么算`、`砖墙的量到底怎么算的`、`这个柱子的工程量是怎么来的` | 在库计量题却 `工具=[]` 自答 / 过度反问 | v5 `<norm_qa>` 硬闸：第一步无条件 tool_search |
| 1b 工具幻觉 | `独立基础和条形基础包含哪些`、`按2013版装配式预制率怎么核定` | 去调不存在的 `norm-qa` 工具 | v5 换真工具名，写死「没有 norm-qa 工具」 |
| 1c 边界自拒 + 编造 ⚠️ | `按GB50011 抗震等级怎么划分`、`gb50016 防火分区`、`GB50010 保护层` | 跳检索直接拒，**且拒答时编造** DBJ15-9-2019 等假号 | v6 拆分「口径超范围只指版本/地区/专业」+ 最高红线「拒答禁编」 |
| 1d 边界金标不一致 | `按2024版装配式评价标准…` | 正确直接拒，金标却标该检索 | 改金标 `expect_route→false`，对齐其它 2024 用例 |

一条 `按GB50011` 能同时踩三雷：红线泛化（误当口径超范围）+ 跳检索 + 编造。**规范问答是唯一「lead 亲自做
agentic RAG + 多步」的能力，弱模型最容易在「先检索」这步掉链子；其余能力都是「直调一个引擎化工具」，天然稳。**

### 能力④ 智能询价（price）

| 子问题 | 触发 query | 现象 | 解法 |
|---|---|---|---|
| 4a 过度反问清晰题 | `水泥这阵子涨了吗`、`这个混凝土现在贵不贵` | 材料已点名，该直接 `price_query`，却反问 | v6 clarify 补「材料已点名的询价直接 price_query」 |
| 4b 违规取数（他省） | `上海本月螺纹钢信息价` | 上海=他省该拒，却调了 price_query | 红线有「他省不取数」但没守住，护栏待加强 |

### 能力②③ 清单匹配 / 定额推荐（bill_match / quota_recommend）

| 子问题 | 触发 query | 现象 | 处理 |
|---|---|---|---|
| 2a 零特征业务缺料：route vs clarify | `这个柱子套什么清单码`、`这块现浇板套什么定额`、`帮我算算这面墙` | 8B 主动反问或 route——两种都合法 | 认了主动反问是对的（revert 重标）；route 也对（假缺口，见问题 9） |

### 能力⑥ 整单组价（cost_workflow）

| 子问题 | 触发 query | 现象 | 解法 |
|---|---|---|---|
| 6a 打转 / 溢出 | `给"C30现浇混凝土独立基础"组价` | 主图打转→撞 32k/递归→`工具=[]` | 评测切第一次决策版（第一跳 break，不执行） |
| 6b 2024 派 task | `按2024国标给"…"组价` | 2024 超范围该拒，却 `工具=['task']` 派子智能体 | v6 红线+路由表补「2024/他省不派 task」 |
| 6c 比选过度反问 | `现浇C30独立基础和预制杯形基础哪个省` | 构件带规格都给了，该各自选码比选，却反问 | v6 clarify 补「构件+规格都给的比选直接 route」 |

### 能力⑤ 智能计算（cost_calc）
基本没冒出独立问题——计算类诉求要么并进组价（⑥）、要么金标里少。这一能力路由较稳。

### 跨能力：域外 / 意图不明（不归某个能力）

| 类型 | 触发 query | 现象 | 处理 |
|---|---|---|---|
| 域外过度反问 | `帮我写个Python爬虫`、`北京这个东西…` | 该直接拒（非造价/他省），却反问 | clarify 补「域外/他省不反问直接拒」；量级小 |
| 真·意图二义（正例） | `这个东西套一下`、`这两种方案哪种更省` | 对象/意图确实不明，`ask_clarification` ✅ | 这才是 clarify 该管的，对了 |

### 从意图分类看到的三个规律

1. **规范问答是绝对重灾区**（4 类子问题，route 失败绝大多数在这）——因为它是唯一「lead 亲自做 agentic
   RAG + 多步」的能力，弱模型最容易在「先检索」这步掉链子；其余能力都是「直调一个引擎化工具」，天然稳。
2. **「过度反问」跨了询价(4a)、组价比选(6c)、域外(F14/G2)三个能力**——共性是**输入带模糊句式但信息其实够**
   （材料点了名 / 规格给了 / 明显域外），弱模型见模糊就想问。解法统一：clarify 里显式豁免这些「其实够」的情形。
3. **「口径边界」也跨能力**：规范(GB50011/2024版)、询价(上海他省)、组价(2024组价)都有——共性是「点名了不
   支持的版本/地区」。规范侧最危险（会编造），询价/组价侧是违规取数 / 误派 task。

## 七、面试常见追问（Q&A 讲稿）

### Q1：为什么用小模型（Qwen3-8B）？不直接上大模型省事？

**核心：不是「只能用小模型」，是垂直行业真实约束 + 分桶策略下的合理选择。**
1. **私有化 / 数据安全**：造价数据、项目清单是客户敏感资产，建筑行业普遍要求本地/私有化部署，不能发云端大模型 API——硬约束，不是偏好。
2. **成本 + 延迟**：路由是高频、延迟敏感的调用（每条消息都过）。大模型按 token 收费、往返延迟高；自部署 8B 边际成本近零、延迟低。高频的活不该每次上大模型。
3. **分桶，不是一刀切**：8B 扛延迟敏感的路由/常规，另注册 32B 留给真推理/选码消歧这类难任务。「合适的活用合适的模型」。

**追问「为什么不直接上大模型」**：大模型也不是银弹——一样会编造、要评测、要防幻觉，只是阈值高些；而**能在弱模型约束下把路由做到 98%，恰恰证明是工程能力在起作用**（评测、归因、显式化、确定性守卫）。这套方法换大模型只会更稳，反过来不成立。

### Q2：skill、subagent 提示词怎么写？

**先亮区别（答对的前提）**：
- **subagent 提示词** = 给一个**隔离独立 agent** 写——自包含（角色 + 工具清单 + **输出契约**），单一职责、返回紧凑结构化；**无用户通道**（单次跑完），缺信息**结构化上抛**（`need_clarification`），不能用 `ask_clarification`。
- **skill 提示词** = 给一段**注入 lead 上下文的指令**写——过程化 runbook（frontmatter + body「第一步…第二步…」），用 lead 自己的工具；**有用户通道**，缺信息可直接 `ask_clarification`。

**关键教训（体现深度）**：我把 `norm-qa` 从 subagent 改成 skill（动因：隔离对单跳规范问答收益有限，且 MCP 跨 loop 崩溃集中在子智能体链）。但发现——**对弱模型，「把关键步骤下沉到 skill」不可靠**：norm-qa 的「先检索」放在 skill 里，8B 不稳定地遵守、很多在库题直接自答。最后把这条**硬闸提回主系统提示词**（`<norm_qa>`）。**原则：弱模型下，skill/subagent 提示词放"细节和话术"，"不可跳过的关键决策步骤"必须留在主图提示词里。**

**具体的坑（证明真踩过）**：skill frontmatter 的 `allowed-tools` 是**全局收窄不是授予**——任一启用 skill 声明它，会把 lead 整个工具面锁进并集、炸掉别的工具。所以给 norm-qa skill **故意没写 allowed-tools**。

### Q3：如果把 lead_agent 换成 32B，之前的 8B 工作还有意义吗？（既然用 32B 为什么之前还做 8B）

**结论：换 32B，8B 工作绝大部分仍有效——产出的资产大多是「模型无关」的。逐条给具体例子：**

**① 评测基建——脚本、金标、指标一个字不改，只是分子变高。**
换 32B 的第一步就是：`config` 切模型 → 跑**同一个** `run_routing_experiment.py --run-name 32b-1` → 看同样的
route/clarify 两率。**「第一次决策」这个测量口径、`route_ok`/`clarify_ok` 的判定逻辑、78 条金标，全部照用**——
你甚至可以拿 v6.yaml + 32B 直接跑一版，和 8B 的 97.78% 同尺子对照看提升。**这套「同尺子跨模型对照」的能力，
本身就是 8B 阶段留下的。**

**② 金标 + 校准——判定跟模型无关，32B 也得遵守。**
- `按2024版装配式评价标准`（A27）我从 `expect_route=true` 改成 `false`（点名2024=口径超范围，该直接拒）——**32B
  也得直接拒**，这条标签不改；
- `帮我给这道墙组价`（零特征）标 `expect_clarify=true`（该主动反问）——**32B 也该反问**，标签一个不动。
金标编码的是「什么诉求算对」，是产品定义，不是 8B 的特性。

**③ 提示词主体——90% 是产品规则，不是「因为 8B 笨」写的。**
32B 的提示词你会**原样保留**：
- **路由表 11 行**（问规范→检索、给特征→`bill_match`、问信息价→`price_query`…）——这是产品的能力映射；
- **「口径固定深圳·2013，点名 2024/他省→拒」**——产品范围裁定；
- **`<red_lines>` 的「编码/条文只能来自工具返回」「拒答禁编」**——安全红线。
**这里没一条是「8B 专用补丁」，删了 32B 照样得有。**

**④ 发现的问题——换模型照样存在，8B 上修好的直接保护 32B（最有说服力，尤其安全）。**
- `按GB50011 抗震等级`（A25）在 8B 上会编造 `DBJ15-9-2019` 假标准号——我因此加了「拒答禁编」红线。
  **32B 一样可能在冷门规范上编造（概率低，但产品里你敢赌一次都不出？），这条红线直接保护 32B**，是我在 8B
  （暴露得频繁、好抓）上发现、写进提示词的安全资产，32B 白捡；
- `上海本月螺纹钢信息价`（C2）的他省护栏、`这块现浇板套什么定额`（B37）的 route/clarify 二义处理——都是**产品级
  问题**，跟模型强弱无关，换 32B 照样要处理。

**⑤ 真正 8B 特有、换 32B 可精简的——就一小撮"给弱模型掰开揉碎"的话术。**
比如 `<norm_qa>` 里「**第一步无条件 tool_search、拿到结果前一字不答、无论多口语**」这种极度显式的硬闸，
和 clarify 里防过度反问的密集正反例（「水泥涨了吗→直接 price_query」「这个东西套一下→要反问」）——**32B
大概率不用喂这么细就能做对**，这部分可以瘦身。但注意：**瘦身是「可选优化」不是「修 bug」，留着也不错，
只是提示词长一点。**

**四个答法角度**：
1. **不是替换，是分阶段/分桶**：8B 是私有化/成本/延迟约束下的默认，32B 后来针对难任务升级。
2. **8B 是更严的「测试床」**：弱模型把问题放大、暴露得更早；在 8B 上抓到的编造/边界泛化/过度反问，32B 一样存在只是更隐蔽——先在低配上摸清坑，换 32B 是"降难度"不是重来。
3. **8B 的评测正是「升 32B」的依据**（最有力）：正因为量出了「哪些任务弱模型稳、哪些不稳」，才有数据决定"哪些值得花 32B 成本"。没有 8B 评测，你不知道该在哪升级、值不值——**用数据驱动模型选型**。
4. **沉淀的是可复用能力**：评测方法论、金标、提示词套路，换任何模型/项目都用得上。

**诚实边界（别夸大，反而加分）**：针对 8B 的极致显式化加固，换 32B 可以精简一部分——但评测、金标、提示词主体、发现的问题全部沿用，且 8B 阶段本身产出了模型选型依据。**要说完全没有 8B 特有的沉没成本不诚实；但主体是可迁移资产，占比小。**

**一句话收尾**：用 8B 不是不知道 32B 更强，而是在约束下先用小模型验证产品逻辑、建好评测金标、同时当严苛测试床把安全/边界问题提前暴露；等评测告诉我哪些任务小模型扛不住，再有依据地升 32B。**这是分阶段的工程决策，不是返工。**
