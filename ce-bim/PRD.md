# ce-bim（BIM 底座层）· 需求与设计 PRD

> BIM 底座层 = **项目 BIM 模型的单一 owner + BIM 原语服务**。本文件是 `ce-bim/` 的需求/设计上下文，改这一层代码前先读。
> 项目级共享上下文见根 `CLAUDE.md`；规范/造价知识层见 `../ce-code/PRD.md`；算量计价（BIM 消费方之一）见 `../cost_agent_prd.md` / `../cost_agent_tech.md`。

BIM 底座层职责：**接收/存储/解析项目 BIM 模型（IFC 优先），对外只暴露 BIM 原语**（`/model` `/elements` `/quantity` `/spatial` `/property`，均按 `GlobalId` 寻址）。IfcOpenShell 解析与 IFC 原件存储**只在此一份**（唯一 owner）。**不含造价扣减/清单/组价**（那是 `ce-cost`），**不含规范校验**（那是审图轨）——上层 N 个消费方做 HTTP 客户端复用，沿用 `ce-code` 已验证的拓扑。

---

## 0. 为什么独立成层（而非埋进 CostAgent）

**BIM 模型是横跨建筑全生命周期的共享资产**，不是算量计价的私有输入：设计阶段（方案比选/限额/规范合规）、施工阶段（4D 进度/碰撞检测）、运维阶段（资产/空间 FM）都消费同一份模型。把共享能力埋进单个消费产品（ce-cost）= 架构错配，未来审图/FM 要复用就得跨产品掏内部代码、必然重写。

**对标项目已验证的模式**：`ce-code`（:8100）把"贵的、共享的知识资产"做成单一 owner 的底座、只暴露原语、N 个 agent 做 HTTP 客户端复用（retrieval 模型只加载一份）。BIM 模型完全是同一类资产——解析/存储贵、被多需求复用——因此与 `ce-code` 平级，独立为 BIM 底座层。

**与 `ce-code` 的正交分工**：

| 层 | 资产性质 | 内容 |
|---|---|---|
| `ce-code`（:8100） | **通用规范/造价知识**（跨项目、带 version 的标准条款/定额） | 防火规范条款库 + 造价数据底座 |
| `ce-bim`（:8102） | **项目 BIM 模型实例**（某项目的几何 + 构件 + 属性，按 GlobalId 寻址） | IFC 原件 + 解析索引 + BIM 原语 |

## 1. 核心设计判断（三条铁律，后面都从这推）

**① GlobalId（IFC GUID）是连接键——整个方案的命门。**
后端 IfcOpenShell 按 `GlobalId` 提取每个构件的几何量/属性；前端 viewer 渲染时每个网格也带原生 `GlobalId`。**只要每条工程量/清单/校验结果都回填来源构件的 `GlobalId`，双栏联动与全链路可追溯就自动成立**：3D 里点构件 ↔ 右侧高亮其量/清单/依据；审核报"异常" → 3D 里直接红色定位。所有消费方共用这一个连接键。

**② 几何只读、量从 IFC 确定性来——底座不参与"猜"。**
呼应项目铁律"能算的不交给模型猜"：构件基础几何量由 IfcOpenShell 从 IFC 确定性提取（`IfcElementQuantity` 或几何计算），**viewer 只负责给人看/点/改**，不让 VLM 去"目测"尺寸。造价专有的扣减规则、清单/组价在 `ce-cost`，规范校验在审图轨——底座只出"中性的"构件量与属性。

**③ 渲染/查看能力做成共享前端包，与底座分离。**
"取数底座"（横切数据/服务）落 `ce-bim/` 后端；"查看/操作"（横切前端 UI）落共享前端组件包 **`ce-bim-viewer`**（web-ifc + Three.js），各产品前端 `import` 同一个 viewer 组件，各自接自己的业务面板与着色逻辑。**给"BIM 查看"单建顶层目录是错的高度**——它是各复核台前端里的一个模块，离不开双栏联动/SSE/回填重算的上下文。

## 2. BIM 原语端点（:8102）

**只暴露 BIM 原语**，被各消费方（ce-cost / 审图 / FM）以纯 HTTP 客户端方式调用：

```
POST /model/ingest                  上传/登记 IFC → 存 MinIO + 解析建索引，返回 model_id
GET  /model/{id}                    取 IFC 原件（前端 web-ifc 渲染拉取）
GET  /model/{id}/elements           列构件（按 type/storey 过滤），每项带 GlobalId + 基础属性
GET  /model/{id}/element/{guid}     单构件：属性 + 基础几何量 + 空间归属
POST /model/{id}/quantity           按 GlobalId 批量取基础几何量（喂给 ce-cost 算量引擎）
GET  /model/{id}/spatial            空间结构树（项目→场地→楼栋→层→构件）
GET  /health                        含 store / parser 依赖地址
```

**边界（明确不做）**：
- ❌ 不做扣减规则 / 工程量清单 / 综合单价（→ `ce-cost`）
- ❌ 不做规范条款校验 / 碰撞检测 / 4D 进度（→ 审图轨 / 未来消费方）
- ❌ 不做几何编辑/建模（底座是只读取数 + 存储，模型修正回填走消费方的 HITL）

## 3. 共享前端 viewer 包（`ce-bim-viewer`）

- **选型**：web-ifc / `@thatopen/components`（IFC.js 系）+ Three.js。纯前端解析 IFC（WASM），开源、内网可用、`GlobalId` 原生可取，与后端 IfcOpenShell **读同一份 IFC**（存 MinIO），渲染几何与取量几何同源、连接键天然对齐，**不需要转换服务、不需要维护映射表**。
- **能力**：拾取/多选高亮、隔离/隐藏（按选择或 IFC 类型/楼层）、剖切面、测量、属性面板、空间结构树导航、**按属性着色**（低置信标红 / 未处理灰显 / 异常红色 / 按类型分色）。
- **联动**：所有交互以 `GlobalId` 为键，与右侧业务表（量/清单/校验）双向高亮；就地修正经各产品的 `PATCH → resume 重算` 回填（重算逻辑在消费方，不在底座）。
- **否决项**：Autodesk APS/Forge（云端 SaaS、要把模型上传到 Autodesk）违反内网私有化 + 造价/项目数据合规，**不用**。
- **升级路径（P1）**：真实项目 IFC 普遍 >100MB、前端解析超时 → 切 xeokit + 后端 XKT 转换（转换塞进 `ce-bim` ingestion 异步管线，转换时把 `GlobalId` 写进 XKT metadata 保住连接键）。

## 4. 消费方矩阵（生命周期需求 → 复用同一底座）

| 消费方 | 阶段 | 用 ce-bim 原语做什么 | 状态 |
|---|---|---|---|
| **CostAgent（`ce-cost`）** | 造价 | 取构件 + 基础几何量（按 GlobalId）→ 叠加扣减/清单/组价 | **第一个消费方（先做）** |
| 模型合规审查（审图轨） | 设计 | 取构件属性 → 与 `ce-code` 防火强条 `applicable_scope` 谓词比对 | 规划（杀手级横切，见 §5） |
| 限额设计 / 方案比选 | 设计 | 取量做早期快速估算与比价 | 未来 |
| 4D 进度 / 碰撞检测 | 施工 | 取空间结构 + 几何关系 | 未来 |
| 资产 / 空间管理（FM） | 运维 | 取构件属性 + 空间树 | 未来 |

---

## 5. 为什么现在就值得立这层——把两条轨焊起来

最有力的论据不是"以后可能有 FM"，而是一个**马上能兑现的横切场景：模型驱动的规范合规审查**。`ce-code` 的防火规范条款库已有结构化 `applicable_scope` 谓词（高度/类型/面积条件）。一旦 BIM 构件属性可按 `GlobalId` 取到（`ce-bim`），就能把"强条谓词 ↔ 模型构件"自动比对——**这是把项目现有规范轨与 BIM 直接焊在一起的用法**。若 BIM 埋在 `ce-cost` 里，审图轨复用就得重写。

---

## 6. 风险与红线

| 风险 | 应对 |
|---|---|
| 共享能力被单产品绑死 | 底座单一 owner + 只暴露原语；造价/审图/FM 一律做 HTTP 客户端，不掏内部代码 |
| 大模型前端解析卡顿 | MVP web-ifc 客户端解析；超 100MB 触发 P1 切 xeokit + 后端 XKT 转换 |
| 连接键丢失 → 联动/追溯断 | `GlobalId` 贯穿底座取量、原语返回、viewer 渲染、消费方回填；转换格式必须保 GlobalId |
| 几何量误差 | 几何走 IfcOpenShell 确定性提取，不让 VLM 目测；量与原件同源可复核 |
| 过度设计 | 见 §7：边界现在划，能力按第一个消费方需要长 |

---

## 7. 落地原则：边界现在划，能力按需长（YAGNI）

**不**现在就把 `ce-bim` 建成完整 BIM 平台（4D/碰撞/FM 全上）。正确做法是解耦与 YAGNI 的折中：
1. **现在**：`ce-bim` 作为独立底座立起来，但**只实现第一个消费方（CostAgent）需要的原语**——按 GlobalId 取量/属性/空间结构；`ce-bim-viewer` 只做造价复核要的交互。
2. **关键是接口而非实现**：把 BIM 原语 HTTP 契约 + viewer 组件契约定清楚，让未来的审图/FM 是"加消费方"而非"重构 ce-cost"。
3. 多花的成本只是"独立目录 + 一层原语 API"，很小；省下的是日后把共享能力从单产品里抠出来的大重构。
