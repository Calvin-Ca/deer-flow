造价 Agent · 目标架构

「先做确定性内核和 benchmark，后接对话皮肤」的落地蓝图 · 五层建造顺序 + 数字验收闸 + 运行时分层 + Agent 定位 · 2026-07
核心纪律：每层通过「无 UI 验收」才允许往上盖；benchmark 不是最后的考试，是每一层的准入闸；皮肤是消费者，永远不许补偿内核。
确定性代码 LLM 触点（可注入/可评测） 数据/金标 HITL 交互 对话皮肤（可替换） Agent 原语（开放任务，收编入籍） 验收闸（不达标不往上盖） 虚线 = 规划中、未建

1. 建造顺序（自下而上，五层五闸）

L0契约层 —— 写代码前先钉死数据形状~半周
原语信封（pydantic 单一源）{step, status, result, provenance{source_type, source_ref, confidence, alternatives}}
路由判定 RouteDecisioncapability / 形态 / 红线 / 置信 / 审计字段
闸 payload 三型confirm / input / review
错误语义表404·501·503 / need_review / no_source（不杜撰的编码化）
验收闸 G0
  • 契约可导出 JSON Schema
  • 上层类型（未来 TS）由 Schema 生成，禁止手抄镜像
▼过 G0 才开工
L1知识原语层 —— 零 LLM 的取数与检索~2–3 周
清单候选召回 bill_matchMilvus 向量 + 结构约束重排（按 spec 版本隔离）
组价取数 price_compose / quotaPG：清单→定额→工料机含量+信息价
规范条文检索BM25 + dense + RRF 混合
每个原语带 CLI 直调入口不依赖任何服务编排即可单测
召回金标 ≥100 条构件描述benchmark/retrieval_eval/
验收闸 G1（数字说话）
  • 召回 Recall@10 ≥ 85%（不达标在本层修分词/embedding/重排，不许上抛给选码层硬选）
  • 取数正确性：抽 50 码人工核对定额/价格零错
  • 全部进 pytest + CI
▼过 G1 才引入 LLM
L2判断原语层 —— 唯一引入模型自治的层：LLM 窄点 ＋ Agent 原语，金标先于实现~2–3 周
候选内选码 select_code接口即评测：select_code(desc, candidates, llm_fn=…)，stub 可测、8b/32b 可对比
套定额消歧 / 缺特征抽取同样可注入、越界作废、不确定标 need_review
置信校准 calibrationcosine 客观分校准自报置信（第一周就会暴露"8b 自报恒 0.95"）——τ 初值在本层定
选码金标 ≥200 条「描述→正确码」金标工具先写（build_match_gold），实现后写
清单生成 Agent（规划）设计说明 → 迭代读文档 + 反复调 bill_match + 自查遗漏 → 清单草表信封（逐项 provenance+置信）
组合套定额规划 Agent（规划）一清单项 → 多定额组合提案（解空间开放，规划枚举是模型强项）
清单核对 Agent（规划）上传 BOQ → 漏项/错套/合理性探索式核对提案
Agent 入籍守则（与 select_code 同规）契约进 · 信封出 · 金标评 · 降级兜 · 只出提案不落账——内部自治关在原语边界内，钉值权在闸和人
验收闸 G2
  • 选码 Top-1 ≥ 80%
  • 置信分桶后，高置信桶实际准确率 ≥ 95%（τ 自动放行的前提）
  • 8b vs 32b 对比表落盘（模型分桶的依据）
  • Agent 原语同规入列：产出必须是带 provenance 的提案信封 + 有金标（如构件抽取召回率）+ 有确定性降级，缺一不收
▼过 G2 才做编排
L3编排内核层 —— 状态机 + 门控 + 确定性路由（stub 跑流程）~2 周
langgraph 可中断组价图compute/gate 双拆 · interrupt/resume · SqliteSaver · 多构件循环
门控 gates（是否跳闸全在代码）τ 双阈值 / 多候选 / 缺价 / 缺政策数；末尾 review 恒停
确定性意图路由 prerouter含 out_of_domain 出口 + 会话粘性入参（prior_capability）
低置信 32b 兜底分类enum+校验+fail-safe；红线闸两条路都确定性
复合编排（拆解→派发→综合）三段固定管线，LLM 失败→确定性降级
验收闸 G3
  • 路由金标 ≥ 95%（含负例：域外句/误判句/承接句）
  • graph 全路径 stub 回归绿（暂停/恢复/回退/半填/what-if，零 LLM 秒级）
  • 一个 shell 脚本纯 curl 走完「描述→总造价」全程
走到这里，产品可靠性上限已全部确定——上面的层只消费、不提高。
▼过 G3 才做入口
L4结构化入口层 —— API 即产品，表单版先于聊天版~1 周
HTTP 会话 API（一等入口）/cost/session/{start,resume,state,rewind,re_rollup}
OpenAPI → TS 类型自动生成G0 契约的兑现：前端类型不手写
朴素调试 UI / 表单版Swagger + 一页表单即可，逐闸办到总造价
验收闸 G4
  • 非开发者能靠表单版独立完成一次组价
  • 闸文案/字段/顺序/依据卡的交互问题在这一层暴露并修完——在它们和"模型行为问题"混在一起之前
▼过 G4 才接皮肤
L5对话皮肤层 —— 最后接、最薄、可替换~1–2 周
lead_agent = 带嘴的手执行注入的路由判定 + 指代消解 + 澄清交互 + 转述；不判断、不编排、不算钱
路由中间件第一天就前置RouteContextMiddleware：每轮先调 /route，判定以 system-reminder 注入（照抄 DynamicContextMiddleware 模式，fail-open）
HITL 握手走结构化通道tool-result 携带 task_id，前端从工具结果取——marker 正则方案从一开始就不会诞生
prompt = 执行手册（~40 行）身份/服从路由/执行规范/红线/风格；零判断规则、零词表散文
皮肤可替换聊天 / 表单 / 飞书机器人共用同一内核（L4 API）
验收闸 G5（行为回归，跑在 trace 上）
  • 20 条对话式请求：该点火的点火、该拒的拒、标记原样传、错误如实转述
  • 皮肤层不含任何判断逻辑的静态检查（prompt diff 审查）

3. Agent 在这张图的哪里 —— workflow 与 agent 的分界

任务性质机制本项目实例为什么
可枚举、顺序固定、要审计 状态机 / 确定性管线 组价 13 步、算钱、汇总、路由红线闸 路径能预先画出来的，不让模型现场决定——错一步是钱，且要可复现可审计
解空间开放、路径不可枚举 Agent 原语（收编入籍） 列清单（设计说明→草表）、组合套定额规划、BOQ 漏项/错套核对、规范多源核证 迭代探索＋组合判断是模型强项、规则枚举不动；自治关在原语边界内：契约进、信封出、金标评、降级兜
会话、指代、澄清、转述 皮肤小 agent（低权限） lead_agent 残留裁量：多轮指代消解、澄清怎么问、结果怎么说 多轮上下文只有模型握着；但判断权已由路由注入上收，它只剩执行权和表达权
这张图不是「不用 agent」，而是「不用不受问责的 agent」：agent 以判断原语身份入籍——内部爱循环几轮循环几轮， 产出永远只是带 provenance 的提案；钉值权在闸和人手里。多 agent 编排（planner + workers + critic）从外面看， 也只是一个更大号的判断原语。

4. 三条设计原则（面试提炼版）

① 契约单一源pydantic 定形状 → JSON Schema → TS 代码生成。三处手抄镜像 = 三处漂移；生成即报错，胜过 5 分钟 Docker build 后才发现。
② benchmark 是准入闸不是期末考金标先于实现;每层数字达标才往上盖。"8b 自报置信恒 0.95"这类事实应在 L2 第一周暴露，而不是接完前端后倒查。
③ 皮肤不补偿内核交互问题在表单版（G4）修完，模型行为问题在 trace 回归（G5）里治——两类问题永不混在同一层调试。皮肤可整体替换,内核纹丝不动。

5. 与「皮肤先行」的对照（实际踩过的代价）

维度皮肤先行（实际发生）内核先行（本蓝图）
