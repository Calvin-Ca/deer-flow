# ce_cost 数据库表详解（11 张表的来源、构造方式与真值等级）

> 配套 `cost/schema.sql`（DDL 单一事实源）的表级说明书：每张表**装什么、从哪来、怎么构造出来、
> 可信到什么程度、在组价链路里扮演什么角色**。速查版见 `DEV.md` §3.1（主键/抽取器一览），
> 本文档是详解版。快照时点 2026-07-07，行数等统计随数据演进会变，结构性结论稳定。

---

## 0. 全景：一条组价链路串起 11 张表

```
bill_spec ──→ bill_quota_map ──→ quota_item ──→ quota_resource ──→ resource ──→ resource_price_map ──→ resource_price
（清单项）      （套哪些定额）      （定额子目）     （用什么/用多少）   （人材机主数据）  （对齐信息价物料）      （当月单价）
                                                                            ↓
                                                    price_composition + fee_rate （钱分几列 / 单价之上乘什么费率）
```

**真值分级**（按"离原文的距离"，消费方据此决定能不能直接当真）：

| 等级 | 表 | 性质 |
|---|---|---|
| 解析真值（逐行搬运） | `bill_spec` `aux_table` `quota_item` `quota_resource` `resource_price` `fee_rate` | 每个值都是原文表格单元格里的值，规则只负责定位/清洗，不产生原文没有的内容 |
| 派生构造（值真，表是造的） | `resource`（跨表去重聚合的维表）、`price_composition`（正文条文关系化） | 值来自原文，但"这张表"在原文里不存在 |
| 建议层（跨源建边，非真值） | `resource_price_map`（纯规则，接近真值）、`bill_quota_map`（规则+LLM，**只建议不定稿**） | 两套编码体系间的映射，原文没有对照表；带 confidence/source，消费方必须看 |
| 空占位 | `hist_bill` | 无生成器无 loader，等未来接脱敏历史工程数据 |

全库唯一碰过大模型的只有 `bill_quota_map` 的 `semantic_llm` 边，其余全部确定性。

## 1. 清单规范库（国标：回答"这个清单项应该长什么样"）

### `bill_spec` — 清单项规范

- **源**：GB/T 50854（房建，2013 + 2024 两版）与 GB/T 50856（安装，2024）的**六列表**
  （项目编码/项目名称/项目特征/计量单位/工程量计算规则/工作内容），每行表格 = 一条记录。
- **管线**：PDF（`data/raw/`，不入 git）→ MinerU 解析（`data/parsed/`）→ splitter 切 chunk 树
  → `cost/bill_spec.py` 按表头分流抽取 → `bill_spec.jsonl` → `load_pg.py` 幂等 upsert。
  非 9 位编码的行落 anomalies 人工抽查，不进库。
- **⚠️ 50500 与本表无关**：GB 50500 是计价标准，**没有**清单项目录（六列表全在 50854/50856），
  不贡献本表任何一行。历史上 50500-2013 的措施项目附录曾被错当 2013 清单源，措施编码体系与
  金标错配（同码不同义），2026-06-18 已切换到正确源 GB-50854-2013 并退役旧产物
  （`notebooks/2026-06-18-1558-2013-switch-gb50854/`）。
- **主键 `(code, spec_version)`**：2013/2024 同 9 位码不同义，必须按版本隔离共存，
  单 code 主键会互相覆盖、令取数串版本。

### `aux_table` — 辅助/参数表

规范里表头**不含**"项目编码"的查表（土分类表、工作面宽度表…），与 `bill_spec` 同一抽取器分流。
列头异构、刻意不归一化，原样存矩形 body + caption + provenance，供工程量计算规则查表。

### `price_composition` — 计价口径（50500 在 PG 里的唯一产物）

- **源**：GB 50500-2024 **正文条文**（不是表格）。2024 版 50500 是纯计价标准，全书可程序化
  关系化的口径就是费用构成两句话，由 `cost/price_composition.py` 用声明式规则
  （RuleSpec：node_path 锚定条文 + 正则抽构成项 + 顿号切分）把散文关系化成每行一个构成项。
- **内容**：总共 10 行——
  - 综合单价构成（条文 2.0.9，6 行，`kind=unit_rate`）：人工费 / 材料费 / 施工机具使用费 /
    管理费 / 利润 / 一定范围内的风险费用（note：不含增值税）；
  - 工程造价构成（条文 3.1.2，4 行，`kind=project_cost`）：分部分项 / 措施项目 / 其他项目 /
    增值税（note：2024 版四部分、无独立规费）。
- **用途**：组价引擎的口径 checklist——综合单价按六项分列，总造价按四部分组装，
  `fee_rate` 的乘数挂 project_cost 层。回答的不是"多少钱"，是"钱分几列"。
- 50500 全文另进 Norm-QA 条文检索索引（BM25 + Milvus），那是向量库、与 PG 表无关。

## 2. 定额库（深圳消耗量标准 SJG 171/170-2024：回答"干这活消耗什么"）

SJG 定额子目表是**转置矩阵**：一张表捆一组子目，列 = 子目、行 = 费用构成 + 工料机。
`cost/quota.py` 按"单位格锚定"矩形化还原（值的列位不固定），一张表三出口：

```
子目编号        | 010001-1        | 010001-2
子目名称        | 实心砖基础 干混砂浆 | 实心砖基础 湿拌砂浆
人工费(元)      | 1200            | 1180          ← 费用行 → quota_item
────── 人工、材料、机械 ──────
人工 | 综合用工   | 工日 | 5.20     | 5.10          ← 工料机行 → resource + quota_resource
材料 | 实心砖     | 千块 | 5.24     | 5.24
```

### `quota_item` — 定额子目

每子目一条：编号/名称/单位/工作内容 + 人工费/材料费/机械费/参考综合单价。书上印的"参考价格"列
（2023-08 快照）**刻意跳过**——价格主源走信息价月刊独立管道，用两年前的快照报价是业务错误。

**编号格式 `6位-N`**（如 `010001-1`）：前两位专业册（01=房建 SJG171，12=土石方 SJG170），
中间四位章/分组，`-N` 组内子目序号。相邻 `-N` 就是原书同一张表里并排的几列。定额编到这么细是因为
**消耗量只有落到"具体做法"粒度才是稳定数字**（干混 vs 湿拌砂浆、泵送 vs 非泵送，人材机全不同）——
这正是 `bill_quota_map` 必然 1:N、以及套定额需要项目特征消歧的因果源头。

### `resource` — 人材机主数据（派生聚合的维表）

**原文没有这张表**——资源名散落在上千张定额表的工料机行里。抽取时按三元组
`(类别, 名称, 单位)` 跨全部表去重聚合（"综合用工"出现上千次 → 收敛成一条），入 PG 发 `id`。

**动机**：组价公式"含量 × 单价"里，含量在定额侧、单价在信息价侧，两个数据源天然不认识对方，
乘法必须有共同落点。`resource.id` 就是这个 join 枢纽——`quota_resource`（量）、`resource_price`
（价）、`resource_price_map`（对齐）三张表都挂它。杠杆效应：对齐/询价工作量从 O(含量行数=几万)
压到 O(资源种类数=一千余)，匹配一次全库生效。也是行业"人材机库"概念（计价软件标配）的最小复刻。

**已知风险**：去重键是字符串级的，直接继承 MinerU 抽取噪声——写法稍异（空格/×x/`$m^3$`）同一实物
就分裂成两条（碎片化）。归一化没做在建表时、推迟到了匹配层（`resource_norm` 只在配价时算归一键）。
失败方向是安全的：键过严 → 该配上的没配上（覆盖率偏低，交询价兜底），不会张冠李戴配错价。
另：`spec` 列定额侧恒为 NULL（规格嵌在 name 里），实际只有信息价侧物料在用。

### `quota_resource` — 工料机含量

子目 × 资源的多对多 + 含量（"010001-1 用实心砖 5.24 千块"）。值直接来自转置矩阵单元格，
破折号（该子目不用此资源）跳过。jsonl 阶段用自然键链接，`load_pg` 解析成 id。

## 3. 价格库（动态独立管道：信息价月更，带时效）

### `resource_price` — 资源价格

- **源**：深圳信息价月刊 PDF（MinerU 解析），价目表逐行搬运。表头有变体，用列名子串定位
  （设备名称=机械 / 项目名称=人工 / 否则=材料），天然排除价格指数/BIM 对比/系数表等非价目表。
- 带 `effective_period`（DATERANGE）时效 + `price_type`（信息价/市场价），排他约束保证
  同资源同来源时效不重叠（按月取价的前提）。**不参与** effective_priority 口径排序——
  价格是动态数据，与静态口径解耦。

### `resource_price_map` — 定额资源 ↔ 信息价物料对齐（建议层里最接近真值的一张）

- **要解决的问题**：两侧同物异名——定额规格嵌名（"干混砌筑砂浆 M7.5"）、信息价 name/spec 分离，
  加 ×/x、全角半角、`$m^3$` 残留、千块↔块口径差，直接精确匹配命中率极低。
- **构造**（`cost/resource_price_map.py`，纯规则零模型）：`resource_norm.canonical_key`
  归一（小写/×→x/去括号空格/拼规格）后**完全相等**才算命中 + 白名单单位换算表
  （千块↔块=1000 等，未登记 = 不可换算）。三态出口：matched（产边，confidence 1.0——
  归一键相等是确定匹配非猜测）/ unit_bad（名规命中但单位不可换算 → **不猜价**，不产边）/
  no_source（信息价没这种料 → 交 HITL 询价）。当前 43 条确定性边。
- **为什么只有 43 条、且不上语义匹配**：实测定性——深圳信息价仅收 ~152 种常用大宗料，
  定额资源约 90% 对不上的原因是**信息价未收录**（专项小料走市场价/询价），缺口是"缺失"
  非"同义"，embedding 几乎零收益反引入猜测风险。宁缺毋造。
- **取价公式**：amount = 含量 × 信息价单价 × unit_factor。

## 4. 关联与参照

### `bill_quota_map` — 清单 → 定额 APPLIES 边（建议层核心，非真值）

清单（GB 50854 九位码）与定额（SJG 编号）两套编码体系互不相通、无官方对照表，此表自建。
当前 542 边 / 127 清单（2024 房建覆盖率 26.9%），来自两条离线管线：

1. **名称匹配种子**（`cost/bill_quota.py`，313 边）：清单名 == 定额名首段 → 0.9，清单名 ⊂ 首段
   → 0.6；两者同属启发式名称匹配，统一 `source='auto_name'`（强弱由 confidence 承载，exact/substr
   方式记入 note）。天花板低（11.2%）：
   定额名前缀式（"非泵送现浇混凝土 独立基础 混凝土"），取首段永远对不上"独立基础"。
2. **清单套定额补全**（`cost/bill_quota_enrich.py`，229 边，2026-07-06 首轮）：
   ① 粗筛（确定性）——清单名 1+2-gram 在定额名中的 IDF 加权覆盖率 + 尾字本体规则
   （中文构件名本体在尾部，候选不含清单名尾字打三折），全量排序取 top-K；
   ② 精判（Qwen3-32B）——三条红线：只能候选内选（越界作废）/ 不适用返回空（不硬配，
   覆盖率虚高比缺口更毒）/ 措施类子目不选（模板/脚手架/支撑是伴随项，代码侧关键词双保险）。
   产边标 `source='semantic_llm'` + LLM 理由入 note，**可按 source 整批回滚**。
   首轮防错实测：诚实空 335 码、红线拦下 30 条越界边。

**定位与消费约定**：这是**建议缓存不是真值声明**——离线管线把昂贵的模糊判定冻结成可审计快照
（每边带 confidence/source/note），在线组价 SQL 带出 confidence 排序返回，低置信多子目的定稿权
在任务层 quota_gate（HITL）。"表管记忆，loop 管裁决"：搬进 agent loop 现算会毁掉可复现性
（同标段两次组价套不同定额，造价无法对账审计）且人工确认无处沉淀。
**待建闭环**：quota_gate 确认结果回写本表（`source='manual'`、confidence 1.0）——
LLM 提候选 → 人确认 → 落库 → 下次直接命中，表随使用收敛向真值。

每边带 `bill_spec_version` 版本隔离（同 9 位码跨版本不同义）；目前只为有兼容定额的 2024 版建边，
2013 定额入库后再补（`SPEC_REGISTRY` 翻 supports_compose）。

### `fee_rate` — 费率库

深圳市建设工程计价费率标准 2023 的 7 张异构费率表（安文/夜间/赶工/总包服务/增值税/附加税/保险），
按 caption 声明式锚定列布局搬运（`cost/fee_rate.py`），caption 不中规则直接跳过计数（宁缺毋造）。
每行：费用大类/名称/适用范围/参考上下限/推荐值/单位（%/‰/系数）。是"综合单价之上算总造价"的乘数。

### `hist_bill` — 历史工程库（空占位）

脱敏历史工程清单单价，供相似案例对标与报价异常检测。**目前无任何生成器和 loader**，
仅建表等未来接数据（[可缓]）。

## 5. 治理约定（消费方必读）

- **口径表强制四治理字段**：`doc_id` / `spec_version` / `region` / `effective_priority`
  （越小越优先，深圳本地=1）。价格表带 `effective_period` 时效，不参与优先级。
- **版本严格隔离**：`bill_spec` 复合主键 + `bill_quota_map.bill_spec_version` 过滤，
  杜绝 2013/2024 跨版本串库（`config.SPEC_REGISTRY` + `resolve_spec` 路由）。
- **建议层消费纪律**：读 `bill_quota_map` / `resource_price_map` 必须带出 confidence/source，
  低置信项走 HITL 闸口，绝不当真值直接定稿。
- **红线**：no_source 一律诚实返回空/None（`price_status="no_source"`），绝不编价、不硬配。
