# 智能体 Benchmark 规范

> 配套文档：`../AGENT_PRD.md`（需求与路由权威源）。本文档定义如何**度量** PRD 中两个 Agent（智能组价 / 规范智能问答）及其依赖能力是否达标。
> 文档定位：把 PRD §8「验收要点」落成**分层、可执行、可复现**的评测体系。
> 文档对：本文定义 **「测什么 / 指标口径」**；**「怎么用 Langfuse 实际跑（前置→灌金标→跑 runner→看分，逐步命令）」见 [`LANGFUSE.md`](LANGFUSE.md) §9 runbook**。即——本文是规范，那份是操作手册；本文某层指标改了，那份对应 runner/`create_score` 名随之对齐。
> 单一事实源约定：路由金标准的依据是 `../AGENT_PRD.md` §4.3 决策表；本文档不重定义路由规则，只定义如何测。§4.3 改了，本文档的路由金标准随之更新。

## 1. 设计原则

benchmark 的形态由 PRD 的架构特征决定，不是套通用 LLM 评测模板。

| 原则 | 来由（PRD） | 对 benchmark 的含义 |
|---|---|---|
| **分层独立评测** | 三层架构 Orchestrator→Pipeline→ReAct | 路由 / 门控 / 检索 / 生成各自一套指标，再加端到端；某层崩了能定位到层，不被端到端分数掩盖 |
| **确定性层用精确指标** | 路由（§4.3）+ 门控（§4.4）在调 LLM 之前完成，是规则/检索打分 | 这部分用分类准确率/混淆矩阵/误直配率，**100% 可复现、可回归**，不靠人评 |
| **脏请求加权** | §8.1「以脏请求 EH-01~04 正确分流率为主指标」 | 评测集按 EH-01~04 **分层超采样**，不用自然分布（自然分布里干净请求占多数，会掩盖路由缺陷） |
| **红线零容忍** | C-04 检索层不算数 | 不是「越界率低」，是 **越界=0 的 gate**：任何一次 RAG 层算数即判该用例 fail |
| **调参 / 评测隔离** | τ_high/τ_low/w₁/w₂ 可调（§4.4） | 评测集切 dev（调阈值权重）/ test（冻结、只跑一次出数），否则是在测试集上调参作弊 |

## 2. 分层 Benchmark 体系（七层）

| 层 | 测什么 | 对应 PRD | 是否机器可判 |
|---|---|---|:---:|
| L1 路由 | 落点分类是否正确 | §4.3 / §8.1 | ✅ |
| L2 置信度门控 | 直配/辅助/ReAct 的分流，误直配率 | §4.4 | ✅ |
| L3 检索 | RAG 召回质量、版本对齐、地域纯净 | C-01/C-02、FR-K | ✅ |
| L4 答案/红线 | 溯源完整、拒答正确、红线零越界 | C-01/C-03/C-04 | ✅（多数） |
| L5 复合拆解 | 复合请求拆得对不对 | EH-01 / FR-X03 | 半自动 |
| L6 Agent 任务级 outcome | 整件事做没做成：任务成功率(终态)、工具调用、忠实度（**详见下方 L6 子节**；schema §4.4） | §8.1、τ-bench/BFCL/RAGAS | ✅ 程序判 + judge |
| L7 NFR | 延迟、多租户隔离、可观测（横切各层/路径） | §8.2 | ✅ 机器 |

### L1 路由 Benchmark（核心）

- **测什么**：给定原始请求，分类器输出的落点是否等于标注落点。
- **数据**：从零按 §4 / §4.1 schema 构建——每条样本标 §4.1 四维信号 + 期望落点 + EH 类型，直接对齐 §4.3 决策表七行与 EH-01~04（构建法见 §7 阶段 1 / 无专家版 §8）。
- **指标**：

| 指标 | 怎么量 / 含义 | 门线 |
|---|---|---|
| 总体路由准确率 | 落点分类整体准确率（§8.1） | ≥ 95% |
| 逐行准确率 | §4.3 七行各出一个数，避免「靠多数类刷高总分」 | 无单行 < 90% |
| 按 EH 类型召回 | 脏请求是主指标，EH-01~04 各单列 | 主指标，逐类看 |
| 混淆矩阵·危险误分 | ①「缺特征组价」误判「高置信直配」（该澄清却直配，最危险）②「动态价格」误判「静态 RAG」（出过期价，违反 C-02 时效） | 两方向 ≈ 0 |

- **通过线**：总体 ≥ 95% 且无单行 < 90%；两类危险误分方向 ≈ 0。

### L2 置信度门控 Benchmark

依赖检索分数，必须与 L1 分开。

- **前置**：评测时**冻结检索结果**，否则检索波动污染门控指标。
- **标注**：每条组价请求标金标「应直配 / 应 LLM 辅助 / 应 ReAct」（造价专家定）。
- **指标**：

| 指标 | 怎么量 / 含义 | 门线 |
|---|---|---|
| **误直配率**（最关键·安全） | 判「置信度≥τ_high 直配、绕开 LLM」但实际匹配错的比例；直配绕过 LLM 兜底，错了直接进结果 | ≤ 1%（最严 gate） |
| 直配覆盖率 / 直配准确率 | 绕 LLM 路径的 precision（§8.1 门控有效性） | 回归基线 |
| ReAct 触发召回 | 该澄清的是否触发 ReAct（漏触发 = 缺特征硬配） | 回归基线 |
| τ/w 调参曲线 | dev 集扫 τ_high/τ_low/w₁,w₂，画 (误直配率 vs 直配覆盖率) 权衡曲线，选点后 test 验证 | 仅 dev 调参 |

- **通过线**：误直配率 ≤ 1%；在该约束下直配覆盖率尽量高（作为回归基线，不设硬线）。

### L3 检索 Benchmark（ce-code RAG）

- **数据**：从零构建召回评测集（清单项 / 定额子目 / 规范条文各一组），可由权威语料反向构造（见 §8 反向构造），不复用既有 `retrieval_eval`。
- **指标**：

| 指标 | 怎么量 / 含义 | 门线 |
|---|---|---|
| Recall@k / MRR | 清单项、定额子目、规范条文各算一组 | 回归基线 |
| **版本对齐召回**（C-01 / FR-K05） | Top-k 命中里版本/年份正确的比例——新旧标准差异类必测 | 回归基线 |
| **地域纯净度**（C-02） | 检索结果非深圳口径泄漏率；EH-03 显式跨省时须带正确地域标注 | = 0 |

- **通过线**：地域泄漏率 = 0；Recall@k、版本对齐召回设回归基线（随库迭代调）。

### L4 答案 / 红线 Benchmark（机器可判）

- **指标**：

| 指标 | 怎么量 / 含义 | 门线 |
|---|---|---|
| **溯源完整率**（C-01） | FR-K/FR-P 答案附「标准号 + 版本 + 条款/子目」的比例；正则+结构校验机器判，缺版本即不完整 | = 100% |
| 拒答率（C-03） | 构造**确知库内无命中**样本，测明确拒答率 | 回归基线 |
| **误拒率**（C-03） | 构造库内有命中样本，测不该拒而拒的比例（防「为了不幻觉乱拒」） | 回归基线 |
| 拒答 F1 | 合成拒答样本上的 F1 | 回归基线 |
| **红线零越界**（C-04） | 插桩计算工具 / RAG 层，统计 RAG 层是否发生数值计算，任何一次 = 该用例 fail | = 0 |

- **数据**：拒答正确性的 `boundary`（越界应拒答）样本从零构造，不复用既有 `routing_eval`。
- **通过线**：溯源完整率 = 100%；红线越界 = 0；拒答 F1 设回归基线。

### L5 复合拆解 Benchmark

路由准确率只看顶层落点，复合请求的难点在**拆得对不对**（FR-X03 结算/变更全靠拆解）。

- **标注**：复合样本标「应拆成哪几个子任务 + 每个子任务的落点」。
- **指标**：

| 指标 | 怎么量 / 含义 | 门线 |
|---|---|---|
| 子任务集合 P/R/F1 | 拆多了（P↓）/ 拆漏了（R↓）/ 拆错落点 | 回归基线 |
| 子任务级路由准确率 | 每个拆出的子任务落点是否正确 | 回归基线 |
| 汇总正确性 | 子任务结果合并回最终答复是否正确 | 回归基线 |

### L6 Agent 任务级 outcome（τ-bench / BFCL / RAGAS 范式）

L1–L4 测「零件对不对」（确定性、单次可复现）；**L6 测「整件事做没做成」**——组价 agent 多轮调工具、自己决策、最终套出的那条定额到底对不对。它吸收并做严了原"端到端任务成功率"（人评 rubric → 程序化 terminal-state + pass^k）。范式不照搬通用 LLM 评测，借三个 agent 专用 benchmark；**与 L1–L4 互补，不可互相替代**。

**与确定性层的本质差异**：

| | L1–L4 确定性层 | L6 agent 任务层 |
|---|---|---|
| 测的对象 | 单个零件（分类器/检索器/格式校验） | 模型+工具+编排的整个系统在环境里跑一遍 |
| 判定方式 | 对照金标签，精确 | 对照**最终状态**（套对定额没/引对条款没），outcome-based |
| 复现性 | 单次确定、可进 CI | 有随机性（LLM 采样），**必须 pass^k 多跑** |
| 主指标 | 准确率/召回/泄漏率 | 任务成功率 + 一致性 + 违规率 |

**三个子层 → 各对标一个范式**：

| 子层 | 对标范式 | 测谁 | 核心指标 |
|---|---|---|---|
| **L6-A 端到端组价任务** | **τ-bench** | cost agent 整体（多轮调 :8100/:8101 → 收敛出价） | 任务成功率（终态判定）+ **pass^k** + **红线违规率（独立列）** |
| **L6-B 工具调用** | **BFCL** | cost/norm agent 的工具选择与参数填充 | 工具选对率 + 参数填对率 + schema 合法率；**量化前后对比** |
| **L6-C 规范问答忠实度** | **RAGAS** | norm-qa agent（本质是 RAG，不是 agent 多步） | faithfulness + 引用准确率 + context precision/recall + answer relevancy |

三条铁律（来自 AGENT_MS 结论）：
1. **pass^k 而非 pass@k**（L6-A/B）：同一 case 连跑 k 次（建议 k=5）全对才算过，专测 Qwen3-8B function-calling 的一致性/不漂移——单次准确率会掩盖"同输入会飘"。
2. **红线违规率独立计分**（L6-A）：把"任务做对"和"有没有违规"拆成两个数，绝不糅进总分；违规率是与 C-04 同级硬 gate（= 0），把 L4 的"红线零容忍"延续到 agent 运行态。
3. **规范问答别套 agent 框架**（L6-C）：最致命的失败是"答得流畅但引错条款号"，是 RAG 忠实度问题，用 RAGAS grounding 指标量，不要塞进 L6-A 终态判定。

**判定方式（怎么自动判）**：
- L6-A 终态：程序化判定器读 `terminal_check`，比定额号/费率区间/溯源结构——**不比答案文本**（outcome-based 的关键）。
- L6-B 工具调用：解析 agent 实际发出的 tool-call，按 `arg_match` 比对，纯程序判，可进 CI。
- L6-C 忠实度：LLM-judge 跑 RAGAS——但 **judge 须先在小批人标样本上校准一致性**，否则是拿不稳的尺子。
- pass^k 聚合：每 case 跑 k 次，"k 次全过"折 0/1 算通过率；单列**漂移率**（k 次不一致占比）观测小模型稳定性。

**三子层从零构建、靠共享 `id` 衔接**（不复用既有数据）：L6-A 的 `difficulty` 与 §4 的 EH-01~04 规格对齐；L6-B 的 `query` 与 L1 路由用同一套合成槽位生成、补 `expected_call`；L6-C 的 `gold_contexts` 由规范语料反向构造（见 §8 反向构造）。

> 任务级 case schema 见 **§4.4**；门线见 **§5**。

### L7 NFR（横切维度）

NFR 不属于某一层，而是**横切各层/路径**：延迟按路径分测、隔离测数据面、可观测测跨层埋点（落点/置信度/来源分别落 L1/L2/L3）。单列成层只为门线归集，不改变其横切本质。

- **指标**：

| 指标 | 怎么量 / 含义 | 门线 |
|---|---|---|
| P95 延迟（§8.2） | 按路径分类测（非单一 E2E 数） | FR-K ≤ 3s / FR-P01 直配 ≤ 2s / ReAct 单轮 ≤ 5s |
| 多租户隔离 | 越权访问用例，跨租户 BOQ/算量不可见 | 不可见 |
| 可观测 | 每次路由落点(L1) / 置信度(L2) / 命中来源(L3) 是否可审计追溯 | 可追溯 |

## 3. 与 PRD §8 的映射

把 PRD §8「验收要点」逐项落成可执行的指标与层。本表只说**测什么 / 用什么方法 / 在哪层**；具体**门线数值统一见 §5**（单一权威源，避免两处漂移）。

| 验收维度 | benchmark 怎么测（指标 + 方法） | 落在 |
|---|---|---|
| 路由正确率 | 总体准确率 + 逐行准确率 + EH 召回；复合请求加测子任务级 P/R/F1（拆得对不对） | L1 + L5 |
| 门控有效性 | 误直配率独立安全 gate（直配绕 LLM，错即进结果）+ 直配覆盖率/准确率 | L2 |
| 溯源完整率 | 答案附标准号+版本+条款；并查版本对齐召回（版本对不对，非只查有没有） | L4 + L3 |
| 拒答正确性 | 拒答率 + 误拒率（防「宁可乱拒」刷分）+ 拒答 F1 | L4 |
| 地域纯净度 | 检索结果非深圳口径泄漏率 | L3 |
| 红线零越界 | 插桩 RAG 层，任何一次算数即该用例 fail | L4 |
| 调参/验收隔离 | dev/test 切分，门控调参只碰 dev（防测试集调参作弊） | §4 |
| NFR | P95 延迟 / 多租户隔离 / 可观测 | L7 |

> 门线数值见 **§5 验收门线汇总**。

## 4. 评测集设计原则与标注规范（schema）

### 4.1 五个设计原则

> **适用范围：全部评测层（L1–L7）通用。** 这五条是任何一个评测集都要守的工艺底线，与具体数据形态无关——无论请求级（L1/L2/L4/L5）、检索召回（L3）、任务级（L6）还是 NFR（L7），都按这五条造。

| 维度 | 做法 |
|---|---|
| 分层抽样 | 按 §4.3 七行 + EH-01~04 + FR-K/P/C/I/X **分层配额**，脏请求超采样，**不用自然分布** |
| 规模建议 | 起步：每个落点 ≥50、每个 EH ≥80（脏请求权重高），总量 ~800–1200，可算 95% 附近置信区间 |
| 切分 | **dev**（调 τ/w/检索参数）/ **test**（冻结、只跑一次出验收数）；门控调参只许碰 dev |
| 标注质量 | 路由标签**双标 + 仲裁**（路由是主指标，标注噪声直接吃掉 5% 余量）；有专家时专家标金标，无专家时按 §8 反向构造 + 异源模型校验定金标 |
| 难例来源 | 真实用户日志里的歧义/缺特征/跨省/复合请求优先入库，比人造样本更能暴露问题；流量未起时先用 §8 合成 + 对抗造难例顶上 |

### 4.2 请求级标注 schema（建议 JSONL，落 `benchmark/routing_eval/`）

**适用范围**：本 schema 标的是"一条请求该怎么走"，仅覆盖请求级评测；其余层各有独立数据形态，不共用本 schema。

| 层 | 本 schema 是否覆盖 | 数据形态 / 落点 |
|---|:---:|---|
| L1 路由 | ✅ 覆盖 | `signals` / `expected_route` / `eh_type` |
| L2 门控 | ✅ 覆盖 | `gate_gold` |
| L4 答案·红线 | ✅ 覆盖 | `expected_sources`（溯源）/ `expect_refuse`（拒答） |
| L5 复合拆解 | ✅ 覆盖 | `expected_subtasks` |
| L3 检索召回 | ⚠️ 仅版本·地域信号 | Recall@k / MRR 需"query → 带排序的金标文档/条文 id"形态，见 §2-L3 |
| L6 agent 任务层 | ❌ 不覆盖 | §4.4 **任务级 schema**（`agent_eval/`，含 `terminal_check`/`policy`/`pass_k`），与本 schema 不同源 |
| L7 NFR | ❌ 不覆盖 | 延迟/隔离/可观测，横切各层/路径，见 §2-L7 |

```jsonc
{
  "id": "RT-0001",
  "query": "C30 现浇矩形柱按特征匹配子目",
  // §4.1 四维信号金标
  "signals": {
    "source": "static",        // static | dynamic
    "context": false,          // 是否需要项目上下文
    "calc": false,             // 是否需要数值计算
    "feature": "complete",     // complete | missing | na
    "intent": "single"         // single | composite
  },
  "expected_route": "组价Agent",     // 期望顶层落点（§4.3）
  "expected_subtasks": [],           // 复合请求：子任务+各自落点（L5）
  "gate_gold": "direct",             // direct | llm_assist | react（L2，仅组价类）
  "expected_sources": [              // C-01 溯源金标
    {"std": "SJG 171", "version": "2024", "clause": "..."}
  ],
  "expect_refuse": false,            // C-03 是否应拒答
  "region": "shenzhen",              // C-02
  "eh_type": null,                   // EH-01..04 | null
  "fr_code": "FR-P01",
  "split": "test"                    // dev | test
}
```

### 4.3 两层路由标注（落点 + 编排，同源新建）

同一个词"路由"在系统里指两件不同的事，分处两个架构高度：**① 落点路由（业务层）**——按 §4.3 这条请求业务上该归谁管（组价/规范/计算/价格）；**② 编排路由（实现层）**——lead agent 在渐进披露下**实际**有没有识别并去调对脚本（`cost.py`/`qa.py`）。新建数据时**一条请求同时挂两层标注、共享 `id` 与 `query`**，不要并成一张表硬塞：

**为什么必须分两层**——"业务上该去组价"和"lead agent 真调了 `cost.py`"会各自独立翻车，糊一起就漏测下表第二行那种隐蔽失败（落点对、实现没落地，弱模型 function-calling 最易栽在这）：

| 落点对吗 | 脚本调对吗 | 说明 |
|:---:|:---:|---|
| ✅ | ✅ | 理想：判对了，也调对了 |
| ✅ | ❌ | **最隐蔽的坑**：业务判断没错，但渐进披露下没认出该调 `cost.py`——只标落点会显示"对"，实际却没干活 |
| ❌ | — | 业务落点就判错了，下游必错 |


| | 落点视角（主） | 编排视角（实现验证） |
|---|---|---|
| 视角 | **PRD §4.3 落点路由**：四维信号 → 组价/规范/计算/价格取数 落点 | **编排层 skill 路由**：lead agent 在渐进披露下能否识别并去调 `qa.py`/`cost.py` 脚本 |
| 关键字段 | `signals`(四维)、`expected_route`(§4.3 落点)、`gate_gold`、`eh_type` | `agent`(norm-qa/cost-agent)、是否调脚本、是否反问版本 |
| 量什么 | L1 逐行准确率 + EH 召回 | 路由率 + 红线遵守率 |

- **谁是主**：PRD §4.3 落点是业务主视角（L1 主指标），编排层是下游实现验证视角（验「落点对了，脚本也调对了」）。以 §4 schema 为骨架，编排字段作附加列挂上。
- **字段映射可推导、可机器校验**：`expected_route=规范问答Agent ↔ agent=norm-qa`、`组价Agent ↔ cost-agent`；`eh_type=EH-02(越界) → expect_refuse=true`；`gate_gold=react ↔ 缺版本反问`（缺版本即缺特征，EH-04）。映射表机器对账，防两层标注漂移。

### 4.4 任务级 case schema（L6 用，落 `benchmark/agent_eval/`）

与 §4.2 请求级 schema 不同——4.2 标"一句话请求该路由到哪"，本 schema 标"一个完整任务的初态、目标、工具环境与可程序化判定的终态"，喂 L6（A/B/C），按子层分文件。

**L6-A 端到端组价任务**（`agent_eval/cost_task/*.jsonl`）：

```jsonc
{
  "id": "TASK-COST-0001",
  "user_goal": "为「C30 现浇矩形柱，柱周长1.8m，泵送」组价",   // 多轮起点，可含缺特征
  "init_context": { "spec_version": "深圳2013", "region": "shenzhen" },  // 项目上下文/版本口径

    "must_cite": [{"std": "SJG 171", "version": "2013"}]   // 终态必须带的溯源
  },
  "policy": {                          // 红线，违反即 case fail（独立计分）
    "no_rag_calc": true,               // RAG 层不得算数（C-04）

    "clarify_if_missing_feature": true // 缺特征必须先 ask 而非硬配（EH-04）
  },
  "pass_k": 5,                         // 连跑次数
  "difficulty": "ambiguous",           // clean | ambiguous | missing_feature | cross_province | composite
  "split": "test"
}
```

**L6-B 工具调用**（`agent_eval/toolcall/*.jsonl`，BFCL 式单步/少步）：

```jsonc
{

  "query": "查深圳2013口径下 C30 现浇矩形柱的定额子目",

}
```

## 6. 落地优先级

1. **P0**：从零搭评测管线——确立 §4 标注 schema（请求级 §4.2 + 任务级 §4.4）与判定脚本，先跑通 L1 路由 + L4 红线两个机器可判层（无需人评，可进 CI 回归）；管线先空跑，待新建数据灌入。
2. **P0**：阶段 1 规则可推导标签层——L1 路由 + L6-B 工具调用，合成 query + 规则/schema 推导标签，专家仅难例仲裁（§7 阶段 1）。
3. **P1**：L2 门控评测 + τ/w 调参曲线（依赖冻结检索结果）。

5. **P1**：**L6-C 规范问答忠实度**——规范语料反向构造 + 专家校验 contexts / 补答案事实点（无专家时按 §8 反向构造出可信金标，见 §7 阶段 2）。
6. **P2**：**L6-A 端到端组价任务**（终态判定器 + pass^5，专家二判定金标，最贵）。
7. **P2**：L5 复合拆解、L7 NFR 压测（延迟/隔离/可观测）。

## 7. 数据集构建路线（方法 × 工艺 标注）

**前提（重要）**：本基准的数据集**全部从零重新构建，不复用任何既有评测数据**。既有 `routing_eval` / `retrieval_eval` 均为**合成生成（方法3）、非人工金标**，**不作种子、不降级沿用、不进新基准**——一律从头按 §4 schema（§4.2 请求级 + §4.4 任务级）重建。排序原则：不按"哪层已有数据"，而按"**哪层的标签最省专家**"——标签可由规则/schema 机器推导的层最先建，需要专家判断的层最后建。**合成的是 input（合法、便宜）；贵的永远是 label。**

构建方法（标准名）：**1 真实日志挖掘** / **2 人工标注** / **3 合成生成** / **4 蒸馏（强模型出银标）**
构建工艺：**㈠** 分层配额超采样 / **㈡** dev/test 切分冻结 / **㈢** 难例闭环 / **㈣** 对抗造难例 / **㈤** 金标可机器校验

**排序主轴**：可信金标成本 = 标签需要多少专家。规则可推导标签（路由落点对 §4.3、工具调用 `expected_call` 对 schema）→ 近乎零专家、最先建；专家判断标签（忠实度事实点、组价终态）→ 最贵、最后建。

> 本项目当前无造价专家可投入标注，凡依赖方法2 人工标注的阶段如何替代落地，见 **§8 无专家版（纯合成+蒸馏）构建方案**。

### 阶段 0｜立 schema + 搭评测管线（0 专家，从零）
- **构建方法**：无数据生产——确立 §4 标注 schema（§4.2 请求级 + §4.4 任务级），写好各层判定脚本（路由对决策表、工具调用对 `arg_match`、终态对 `terminal_check`），**不灌任何旧数据**。
- **构建工艺**：㈡ 切分规约（dev/test 目录与冻结流程先定好）；㈤ 判定脚本进 CI（先对样例 sample.jsonl 自测）。
- **产出**：空管线就绪，schema + 判定器 + CI 钩子齐备，待阶段 1 起新建数据灌入。

### 阶段 1｜规则可推导标签层（最先建可信金标）
L1 路由 + L6-B 工具调用——标签由 §4.3 决策表 / 工具 schema 机器推导，合成 query 配规则标签即得可信金标，专家几乎不碰。
- **构建方法**：【3 合成生成】铺 query（路由：构件×强度×部位×是否带版本×单/复合 槽位枚举；工具调用：参数枚举）+ 标签规则推导 +【2 人工标注】仅难例仲裁。
- **构建工艺**：㈠ 分层配额（§4.3 七行 + EH-01~04 超采样、不用自然分布）；㈣ 对抗造难例（"该澄清却像直配""动态价伪装静态 RAG"、缺特征伪直配）；㈤ 标签机器校验（路由对决策表、工具调用对 `arg_match`）；L6-B 量化前后对比（fp16 vs int4）；㈡ 冻结。
- **专家投入**：低（仅 ~20% 难例仲裁）。
- **产出**：L1 逐行准确率 + EH 召回 + 混淆矩阵；L6-B schema 合法率 + 量化掉点。

### 阶段 2｜L6-C 规范问答忠实度（专家判断层，先做便宜的）
从零构建：不复用既有 `retrieval_eval`，`gold_contexts` 由**规范语料反向构造**新生（从条文反推问题，详见 §8 反向构造）；有专家时专家校验 contexts + 补 `gold_answer_points`，无专家时走 §8 反向构造 + 异源模型校验。
- **构建方法**：【3 合成生成 / 1 真实日志挖掘】出问题 +【4 蒸馏】强模型起草候选答案 +【2 人工标注】校验 contexts + 勾 `gold_answer_points`。
- **构建工艺**：㈤ 引用结构化机器校验；**judge 一致性校准**（20 条人-judge 对齐再放量）；㈡ 先 dev 后 test。
- **专家投入**：中。
- **产出**：RAGAS faithfulness + 引用准确率（含库内无命中应拒答对照）。

### 阶段 3｜L6-A 组价终态（最贵，最后）
- **构建方法**：【1 真实日志挖掘 / 3 合成生成】给题（初态 + 用户目标）+【4 蒸馏】强模型出候选定额 + 费率 +【2 人工标注】专家二判定金标。
- **构建工艺**：㈢ 难例闭环（pass^5 → 看错例 → 同类回灌）；㈣ 对抗造难例（缺特征硬配、跨省口径混入）；㈠ 按 `difficulty` 配额；㈤ `terminal_check` + `policy` 结构化机器判。
- **专家投入**：高（每条标全终态 + 红线）。
- **产出**：pass^5 任务成功率 + 红线违规率（独立列）。

### 总览表（方法点名 + 标签性质）

| 阶段 | 层 | 标签性质 | 构建方法（点名） | 构建工艺 | 专家 |
|---|---|---|---|---|---|
| 0 | 立 schema + 管线 | —（无数据生产） | 定 §4 schema（§4.2+§4.4）+ 判定脚本，不灌旧数据 | ㈡㈤ | 0 |
| 1 | L1 路由 + L6-B 工具调用 | **规则可推导** | 【3 合成】query +【2】仅难例仲裁 | ㈠㈣㈤ + 量化对比 + ㈡ | 低 |
| 2 | L6-C 忠实度 | **专家判断** | 【3/1】出题 +【4 蒸馏】起草 +【2】校验contexts+补事实点 | ㈤ + judge校准 + ㈡ | 中 |
| 3 | L6-A 组价终态 | **专家判断** | 【1/3】给题 +【4 蒸馏】候选 +【2】二判 | ㈢㈣㈠㈤ | 高 |

**贯穿规律**：方法 **3 合成**负责量、方法 **2 人工标注**负责准、方法 **1 日志**负责难、方法 **4 蒸馏**负责省专家；工艺 ㈡ 冻结、㈤ 机器校验**每阶段必挂**（防作弊、防漂移是底线），㈠㈢㈣ 按层选用。

**与 §6 的关系**：本节排序与 §6 落地优先级一致——按"标签最省专家"排，规则可推导的 L1/L6-B 先行、专家判断的 L6-C/L6-A 后置；确定性层 P0、NFR P2 不变。全部从零构建、不复用既有数据。

## 8. 无专家版构建方案（纯合成 + 蒸馏）

**适用前提**：本项目当前**无造价专家可投入标注**，手上只有**方法3 合成生成**与**方法4 蒸馏**。§7 是有专家时的完整路线；本节是同一方案在"无专家"约束下的**可执行子集**——目标是在「模型自判的假金标」和「干等专家」之间，**尽可能多地造出可信金标**，做不出的诚实退为 silver 占位。数据同样**从零构建，不复用既有 `routing_eval` / `retrieval_eval`**。

### 8.1 三招：无专家也能出可信金标

1. **规则可推导标签**（L1 路由 / L6-B 工具调用）：标签由 §4.3 决策表 / 工具 schema 机器推导，**机判即金标，本就不需专家**——这部分不受无专家约束。
2. **反向构造（reverse construction）from 权威语料**（无专家版主引擎）：不"先有题再标答案"，而**先锁定权威条目（定额子目 / 规范条文）→ 反推应命中它的 query → 标签 = 该条目本身（构造即真）**。把"标注"变成"对语料的机器可校验溯源"，**同时绕开专家和模型自判**。造价/规范的真值本就在库里（定额库、GB50016/SJG 条文），这招才成立。
3. **跨模型共识蒸馏（cross-model consensus）**：确需蒸馏判断时，**生成模型 ≠ 评判模型**，用 N 个**异源**强模型投票，仅留高一致项为"共识 silver"，低一致进待办。**严禁同一模型自问自答自判**（§4 假金标红线的循环形态）。

### 8.2 三档数据质量（决定能否进 test）

| 档 | 来源 | 可信度 | 用途 | 标记 |
|---|---|---|---|---|
| **机判金标** | 规则推导 + 反向构造（可对语料校验） | 高 | **可进 test 验收** | `gold` |
| **共识 silver** | 跨模型高一致蒸馏 | 中 | dev + 回归护栏，不单独作硬验收 | `silver` |
| **单模型草稿** | 单模型蒸馏 / 低一致 | 低 | 仅 dev 冒烟 | `draft` |

### 8.3 逐层落地（无专家版）

- **L1 路由 / L6-B 工具调用** → **完整可做、输出 test 金标**。方法3 合成 query + 规则标签 = 机判金标；原需专家的难例仲裁改用**跨模型共识**，分歧项标 `silver` 不进 test。
- **L6-C 规范问答忠实度** → **反向构造做出接近金标**。从 GB50016/SJG 条文库随机取条文 c → 强模型据 c 生成问题 q（硬约束"答案须完全来自 c"）→ `gold_contexts=c`（构造真）、`gold_answer_points`= 从 c 抽取的事实句（可对 c 正则校验）→ **另一异源模型**校验"q 的答案是否真在 c 内且唯一"，通过即 `gold`、否则弃。RAGAS 的 reference 就是 c，机器可判。
- **L6-A 组价终态** → **主干可机判、容差与多义挂 silver**。从定额库取已知子目 + 费率 → 反向构造清单项 → `terminal_check.expected_quota / fee_band` 由库直接取（机判真）。两处退 silver：① "构件描述↔子目"非唯一映射的多义项，按库映射规则能定的进 `gold`、不能定的弃入待办；② 费率容差区间宽窄无专家定标，先用库值 ± 工程经验默认带、标 `silver` 待专家收紧。

### 8.4 无专家版的硬边界（必须诚实声明）

1. **语料无唯一真值、要靠行业判断的，做不出金标，只能 silver**：组价合理性（不止套对、还要合规省钱）、费率容差宽窄、规范跨条款综合判断、复合任务拆解合理性——这些 §7 里靠方法2 专家的，无专家版**只能占位、不能验收**。
2. **反向构造的系统性偏差**：题源自"已知答案反推"，分布与真实用户提问不同（真实用户更脏、更省略、口语化）。用方法3 加噪 / 口语化改写缓解，但**消除不了**——评测报告必须**声明"非真实分布"**，不可当真实流量表现宣称。
3. **共识 silver 不是金标**：跨模型一致只降低随机错误，**消不掉系统性共错**（所有模型都被同一规范误导时一致地错）。silver 永远等专家追认才升 gold。

### 8.5 落地序（无专家版 P0→P1）

1. **P0**：L1 路由 + L6-B 工具调用——规则标签机判金标，立即可跑、进 CI（无专家版的确定性收益全在这）。
2. **P1**：L6-C 反向构造金标——条文库反推 + 异源模型校验，跑出第一个可信 RAGAS 数。
3. **P1**：L6-A 反向构造主干（定额库反推终态）+ 容差/多义 silver 占位。
4. **挂起待专家**：8.4 列的判断类指标、L6-A 费率容差收紧、复合拆解合理性——专家到位后按 §7 把 silver 升 gold。

> 一句话：无专家不等于做不了——**规则可推导的直接机判成金标，权威语料能反向构造的把"标注"变成"对库溯源"也成金标；只有真要行业判断的退成 cross-model silver 占位等专家**。这恰好把 §7 的方案在当前约束下切出一个能立刻开工的可信子集。
